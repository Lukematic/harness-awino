PROCEDURE osmani-api-design (define the interface contract before the implementation; PLAN phase):
Design stable interfaces that are hard to misuse — good interfaces make the right thing easy and the wrong thing hard. This covers REST endpoints, module boundaries, component interfaces, and any seam where one piece of code (or one agent's work) talks to another. The contract is written FIRST; implementation follows.

1. CONTRACT FIRST: define the interface before implementing it. Types ARE the documentation — every endpoint/function gets typed input and output, the error shape, and the invariants. Nothing is implemented until the seam can be read by someone who never saw the builder's reasoning.
2. HYRUM'S LAW AT EVERY SEAM: with enough consumers, every observable behavior becomes a depended-upon contract — documented quirks, error message text, timing, ordering. Be intentional about what you expose; do not leak implementation details through the seam (if users can observe it, they will depend on it); plan deprecation AT DESIGN TIME (how a consumer migrates off this interface before v2 exists). Tests are not enough: contract tests pass while real consumers break on undocumented behavior they depend on.
3. ONE CONSISTENT ERROR SEMANTIC: pick one error strategy and use it everywhere — one error body shape (machine code + human message + details), one status mapping (400 invalid data, 401 unauthenticated, 403 unauthorized, 404 not found, 409 conflict, 422 semantically invalid, 500 server error with no internals exposed). Never mix throw/return-null/{error} across the same seam — the consumer must be able to predict behavior.
4. VALIDATE AT BOUNDARIES, TRUST INTERNALS: validate where external input enters (route handlers, form submissions, third-party responses — always treat third-party data as untrusted, config/env loading). After validation, internal code trusts the types. Validation scattered through internal code is the seam telling you it does not trust its own contract — fix the contract instead.
5. PREFER ADDITION OVER MODIFICATION: extend without breaking — new fields are optional, never change a field's type or remove one in place. If the interface is consumed by more than the current mission, breaking changes are versioned and migration-planned (see Hyrum's Law), not silently shipped.
6. IDEMPOTENCY WHERE RETRY IS POSSIBLE: any state-changing endpoint the caller might retry HONORS an idempotency key — accepting the key without honoring it is worse than no key (the client now believes retrying is safe). Key derived from the INTENT, never from the attempt (client-generated or derived from an immutable identifier — never a fresh UUID/timestamp per retry). CLAIM ATOMICALLY: let a unique constraint pick the winner (check-then-act is a race, not a guard). Same key with a different payload fails LOUDLY (client bug) instead of replaying the wrong response. Decide up front what an in-flight duplicate gets (reject 409, wait bounded, or return pending 202) — never let the second caller through because the first "seems stuck". Every call has three outcomes, not two: success, failure, UNKNOWN — record the intent BEFORE calling out, so a timeout leaves evidence to resolve rather than a silently retried effect. Key retention must outlive the longest retry chain (dead-letter replays, dispute windows), not the disk budget.
7. PREDICTABLE NAMING: resources as plural nouns (no verbs in paths), one casing convention, booleans prefixed is/has/can, enums UPPER_SNAKE. List endpoints paginate from day one; PATCH takes partial objects; input types and output types are separate (server-generated fields live on the output, not the input).
