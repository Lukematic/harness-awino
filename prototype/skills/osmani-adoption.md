PROCEDURE osmani-adoption (greenfield vs brownfield path selection; DEFINE phase):
When a mission starts, determine which path you are on FIRST — the discipline you apply depends on it. Applying the greenfield lifecycle to legacy code produces specs for code that already exists and refactors without safety nets.
1. WHICH PATH: greenfield = codebase days-to-weeks old, you control test coverage from day one, conventions defined as you go, low blast radius from a bad change. Brownfield = months-to-years old, uneven or missing test coverage, established-but-undocumented conventions, a bad change can break things nobody remembers how to fix. In between (young but already shipped): start brownfield, accelerate. The mission planner follows lifecycle-sequence (the ordered skill chain per task type) as the map; this skill determines which path the map takes.
2. GREENFIELD — full lifecycle from day one: DEFINE the spec before building (prototypes become products; the spec is the cheapest artifact); PLAN the breakdown; BUILD test-driven in thin slices with atomic commits; REVIEW every change; SHIP behind the readiness gates. Always-on from commit one: TDD, atomic-commit git discipline, security-from-start, ADRs for the first architectural decisions (the ones nobody will remember the why of in two years). Anti-patterns: skipping the spec for "prototypes"; loading every skill into every session (load by phase); deferring observability until "there's something to observe."
3. BROWNFIELD — verification-first sequencing:
   - PHASE 1, CONTEXT AND READ-ONLY: write down the REAL conventions (the ones in the code, not the wiki) — build/test commands, directory meaning, known landmines ("don't touch legacy/billing: no tests, three known workarounds"). Review incoming changes (zero-risk, immediately valuable) and fix bugs with reproduce-first discipline before modifying anything structural.
   - PHASE 2, CHARACTERIZATION TESTS BEFORE CHANGE — HARD RULE: for untested legacy behavior, write characterization tests that pin down what the code CURRENTLY DOES, right or wrong, BEFORE any modification. No refactor of untested code, ever. This is the single most expensive shortcut in brownfield work. Rigor requires regression tests for bugfixes; this rule is stricter — characterization tests precede ANY modification of untested legacy code, and the judge enforces it where feasible (a diff touching untested legacy files with no accompanying characterization tests is rejected).
   - PHASE 3, TWO-SPEED: new features get the full greenfield lifecycle; legacy code stays under the read-only/test-first regime. At the seams, design the boundary contract-first (Hyrum's Law: someone depends on every observable behavior, including the bugs). Declare in the spec which legacy surface the feature may and may not touch.
   - PHASE 4, PAY DOWN: deprecate and remove zombie code deliberately (shrink the legacy surface, don't just wrap it); retrofit observability along the paths actually debugged; optimize only what measurement proves is the bottleneck.
   - ANTI-PATTERNS: big-bang adoption; refactoring untested code; skipping context ("the code is the documentation" — the agent will infer conventions from the worst file it reads); treating legacy behavior as wrong by default — CHESTERTON'S FENCE: the weird retry loop may be load-bearing; understand, then change; ratcheting nothing — each phase adds a gate that doesn't come back off (osmani-constraints), and if a month in you can't name what's newly enforced, the rollout stalled.
4. CONVERGENCE: both paths end in the same steady state — full lifecycle for new work, always-on TDD and git discipline, review gates before merge, skills loaded by phase. Greenfield gets there in days; brownfield in a quarter, via the safety nets the old codebase never had.
