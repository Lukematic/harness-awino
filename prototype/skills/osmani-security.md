PROCEDURE osmani-security (threat-model-first hardening; BUILD and REVIEW phases):
Security is a constraint on every line that touches untrusted data, auth, or external systems — not a phase. At BUILD it shapes the code as written; at REVIEW it audits the diff.
1. THREAT MODEL FIRST (five minutes, before hardening): map trust boundaries (where does untrusted data cross in — user input, files, webhooks, LLM/model output, another process's command line, filenames on shared volumes); name the assets (credentials, PII, money movement, admin actions); run STRIDE-lite per boundary (spoofing, tampering, repudiation, disclosure, DoS, elevation). If you cannot name the boundaries, you are not ready to secure the feature. Write abuse cases next to use cases — "how would I misuse this?" becomes the first test.
2. ALWAYS (no exceptions): validate all external input at the system boundary; parameterize every query — never build SQL/shell from strings; encode output (never bypass framework escaping); HTTPS for external comms; hash passwords (bcrypt/scrypt/argon2, never plaintext); security headers on responses; httpOnly+secure+sameSite session cookies; run the native dependency audit against the committed lockfile before release.
3. ASK FIRST (human approval required): new/changed auth flows, new categories of sensitive data (PII, payment), new external integrations, CORS changes, file uploads, rate-limit changes, elevated permissions. In Awino these map to consequential tools — the existing approval flow is the mechanism; the skill is the judgment of what counts.
4. NEVER: commit secrets to version control; log sensitive data; trust client-side validation as a boundary; eval()/raw-HTML with user data; store auth tokens in client-accessible storage; expose stack traces or internals to users.
5. DESTRUCTIVE PATHS: a delete/move/overwrite is only as safe as the value naming its target. Trust follows who WROTE the value, not the channel: another process's command line is as attacker-controlled as a form field. Require: resolved target (symlinks resolved) under an allowlisted root, at least one level below that root, ownership evidence read before the operation. On refusal, log and stop — never fall back to a broader path. (Awino's Sandbox._resolve enforces the root check; this skill adds the depth/ownership judgment.)
6. SERVER-SIDE FETCHES: any user-influenced URL can aim at internal services (SSRF). Allowlist scheme+host, reject private/reserved addresses, forbid redirects.
7. LLM OUTPUT IS UNTRUSTED INPUT: never into eval, SQL, shell, or a file path. Parse defensively, validate against a schema, then encode. The system prompt is not a security boundary — enforce permissions in code. Keep secrets, other tenants' data, and the full system prompt out of the context window.
8. PRIVACY: classify fields as added (non-personal/PII/sensitive); collect only against a stated purpose — "might need it later" is breach scope, not a purpose; set retention up front and actually delete (backups, caches, indexes included); keep PII out of telemetry and LLM vendor calls without consent and a data-processing agreement.
9. DEPENDENCIES: one installation boundary, one lockfile; review the lockfile diff (most installed packages were never directly chosen); never blanket-approve install scripts; audits match known advisories only — review new packages for typosquatting/ownership/provenance; upgrade one dependency per change, read the changelog (semver is a promise, not a guarantee), verify with a green suite before and after.
10. REVIEW-TIME AUDIT (REVIEW phase): walk the diff against the red flags — unvalidated input into queries/shell/HTML, missing auth checks, wildcard CORS, no rate limit on auth endpoints, secrets in the diff, stack traces in responses, user-influenced server fetches, model output into sinks. Zero unresolved Critical findings is the PASS bar.
