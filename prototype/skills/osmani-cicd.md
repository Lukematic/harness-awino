PROCEDURE osmani-cicd (automated quality gates on every change; SHIP phase — but the pipeline itself is set up during BUILD):
CI is the enforcement mechanism for every other skill: it catches what humans and agents miss, consistently, on every single change. SHIFT LEFT: a bug caught in linting costs minutes; the same bug in production costs hours — move checks upstream (static analysis before tests, tests before staging, staging before production). FASTER IS SAFER: smaller batches and more frequent releases reduce risk; a deploy with 3 changes is easier to debug than one with 30.

1. SET UP ON DAY ONE: the pipeline exists before the first feature lands — projects without CI accumulate broken states, and "we will add CI later" is how that happens. Setting the pipeline up is BUILD-phase work; running it on every change is the SHIP-phase gate. Every change passes, in order: LINT -> TYPE CHECK -> UNIT TESTS -> BUILD -> INTEGRATION -> E2E (where it exists) -> SECURITY AUDIT -> BUILD/SIZE CHECK. NO GATE CAN BE SKIPPED: lint fails -> fix lint, never disable the rule to make it pass; test fails -> fix the code, never skip the test. The gate order mirrors osmani-constraints' cost placement (fast checks first), and the constraints record's FLOOR is exactly what CI enforces mechanically.
2. FEED FAILURES BACK INTO THE LOOP: CI output is the debugger's input. A failed run is copied verbatim to the agent ("the pipeline failed with this error: [specific error]. Fix it and verify locally before pushing again.") — lint failure -> run the fixer and commit; type error -> read the location and fix the type; test failure -> the debugging discipline (osmani-tdd prove-it pattern); build error -> check config and dependencies. The loop closes only when the same change passes; re-running a flaky test until it goes green is masking, not fixing — flakiness gets fixed or the test gets quarantined with a reason.
3. PROTECT THE BRANCH: required status checks must pass before merge; at least one approval; no force-pushes to main. CI runs on every PR and every push to the release branch. A red build is the highest-priority work in the project — when it breaks, it gets fixed or reverted immediately (the Build Cop rule: whoever keeps the pipeline green owns it, and "broken but someone else's" is not a state).
4. DEPLOY SAFELY: every PR gets a preview deployment for manual verification. Staged rollout: main -> staging (auto) -> production (auto after staging verification or manual trigger) -> monitor a defined window -> errors detected: ROLLBACK; clean: done. Decouple deployment from release with FEATURE FLAGS: ship code behind flags, merge early, enable when ready, roll back by disabling (no redeploy), canary 1% -> 10% -> 100%. Flags have a lifecycle — create, enable, canary, full rollout, REMOVE the flag and dead code (set a cleanup date at creation; a flag that lives forever is technical debt). Every deployment is reversible: the rollback mechanism is written and tested BEFORE the deploy, never improvised during an incident. (This is the pipeline half of osmani-shipping's rollback-before-deploy rule.)
5. SECRETS AND ENVIRONMENTS: .env.example committed (template), .env never committed, CI secrets in the secrets manager (never in code or CI config files), production secrets in the deployment platform/vault — CI never holds production secrets. Even CI-only test databases use secret-managed credentials: the habit is the protection.
6. OPTIMIZE, DON'T SKIP: when the pipeline exceeds ~10 minutes, in order: cache dependencies; run jobs in parallel (split lint/typecheck/test/build); run only what changed (path filters); shard test suites (matrix); move slow tests off the critical path onto a schedule; larger runners last. "CI is too slow" is an optimization task, never a reason to bypass a gate. Keep the pipeline green and fast enough that nobody is tempted to go around it.
7. STRUCTURED CI FAILURE DIAGNOSIS — a red build is debugged, not stared at:
   - STAGE/STEP BREAKDOWN — which stage failed, which step inside it, and what ran before it. A failure in "deploy" caused by "build" producing a bad artifact is a BUILD failure, not a deploy failure — fix it where it broke. Follow chained failures: multiple failed steps may share one root cause.
   - TIMING AND BOTTLENECKS — how long each stage took versus its baseline. The slowest stage is the optimization target (see section 6), not the failure — distinguish "slow" from "broken". A stage that is both slow AND failing is two problems; fix the failure first.
   - LOG TRIAGE — read the full error and the stack trace before theorizing; check ALL failed steps, not just the first; tail the failed step's logs (the last ~120 lines usually hold the cause). Quality of diagnosis beats speed: a wrong diagnosis wastes more than a thorough one.
   - FLAKY VS REAL — the determination, in order: does it fail on re-run with no changes? (flaky). Does it fail on main without this change? (pre-existing). Does it fail only with this change? (real). A flaky test is fixed or quarantined WITH A REASON — re-running until green is masking, not fixing (see section 2).
   - FIX-FORWARD VS REVERT — revert when the cause is unclear, the blast radius is wide, or the fix will take longer than the revert. Fix forward when the cause is understood, the fix is small and reviewable, and the pipeline is the only thing red. The decision is recorded, not improvised: "reverted because cause unknown" is a complete sentence. A reverted change can always re-land; a broken main poisons every other change in flight.
