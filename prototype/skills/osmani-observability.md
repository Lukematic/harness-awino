PROCEDURE osmani-observability (instrument the user's system as you build, not after; BUILD phase):
SCOPE: this skill instruments THE USER'S PROJECT — the system being built. (The harness's own traceability is its effect journal and skill pins; do not confuse the two.) Code you cannot observe is code you cannot operate. Instrumentation is written alongside the feature the same way tests are: if a feature ships without telemetry, the first user-reported bug becomes archaeology instead of a query.

1. DEFINE "WORKING" BEFORE INSTRUMENTING: telemetry without a question is noise. Write down 2-4 questions an on-call engineer will ask about this feature (what fraction succeeds first-try vs after retry; when it fails permanently, WHY; is the dependency slower than usual). Every signal below must help answer one of these. If you cannot name the questions, you are not ready to instrument — you will log everything and learn nothing.
2. PICK THE RIGHT SIGNAL PER QUESTION: metrics tell you THAT something is wrong (rate/errors/duration — RED on every endpoint and external dependency; USE for resources), traces tell you WHERE (one slow request broken down by hop), logs tell you WHY (this specific case). Logs: structured JSON with stable event names and machine-readable fields — never string interpolation. CORRELATION IDs are mandatory: generated (or accepted) at the system boundary, attached to every log line, span, and outbound call. When several entry points write one log, NAME THE ENTRY POINT next to the correlation ID (propagated the same way) — a field that merely correlates with an entry point is a hint, not an attribution. Log levels used consistently: error (invariant broken — investigate), warn (degraded but handled — watch trends), info (significant business event), debug (off in production). NEVER log secrets, tokens, passwords, or full PII — telemetry pipelines are a classic leak path; allowlist fields, never whole request bodies. (osmani-security's destructive-path/privacy rules apply here first.)
3. METRICS WITH BOUNDED CARDINALITY: labels come from small fixed sets (route template, status class, provider name) — NEVER user IDs, raw URLs, error message text, or request IDs (that is the cardinality bomb; unbounded values belong in logs and traces). Latency is a histogram, never an average — read p50/p95/p99; an average hides the 1% of users having a terrible time.
4. TRACING: use the vendor-neutral standard (OpenTelemetry) with auto-instrumentation for HTTP/gRPC/DB clients; add manual spans only around meaningful internal units of work, with the attributes on-call will filter by. Propagate context across every async boundary (headers, queue metadata) or the trace dies at the gap. Sample head-based at a low rate; keep 100% of errors if tail sampling is available.
5. ALERT ON SYMPTOMS, NOT CAUSES: symptom (error rate > threshold for N minutes, p99 latency over SLO, queue age) pages a human; cause (CPU at 85%, a pod restarted) goes to a dashboard. Every alert: actionable (if the response is "ignore it", delete it); links to a RUNBOOK (three lines minimum: what it means, first query to run, escalation path; stored where on-call looks); threshold + duration justified by the SLO or historical data; TWO severities only — page (user-facing, act now) and ticket (degradation, act this week). A third tier becomes noise that trains everyone to ignore everything. Update the runbook every time it was used in an incident — a stale runbook builds false confidence.
6. VERIFY THE TELEMETRY ITSELF: instrumentation is code; it can be wrong. Before calling the work done: force an error in staging and find it by correlation ID (fields structured, not [object Object]); confirm metric series appear with expected labels and sane values; follow one request end-to-end in the tracing UI with no broken spans; fire each new alert once (lower the threshold temporarily) and confirm it reaches the right channel with a working runbook link. This is the observability half of the shipping pre-launch gate.
