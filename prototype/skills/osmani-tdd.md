PROCEDURE osmani-tdd (red-green-refactor as engineering discipline; BUILD phase):
rigor-proof-cycles gives the oracle-first thin-slice cycle (RED/GREEN/REFACTOR per behavior). This skill is the discipline around it: how to write tests that prove things, and the habits that keep the suite honest. Without tests, an agent is guessing — plausible code is not correct code.
1. DISCOVER THE STACK FIRST: the cycle is universal, the commands are not. Before the first test, find this repo's test command (package.json, Makefile, pyproject, CI workflows), how to run one focused test vs the full suite, and where tests live. Use the repo's commands for every RED, GREEN, and verification step — never assume a default.
2. RED: write ONE failing test for one behavior. Run it and CONFIRM it fails with a meaningful message. A test that passes without implementation is tautological — investigate. For bug fixes, the PROVE-IT PATTERN: reproduce the bug with a test BEFORE attempting the fix (report arrives -> failing test confirms the bug -> fix -> test passes -> full suite, no regressions).
3. GREEN: write the MINIMUM code to pass. Not clean, not elegant — the simplest thing that passes. Then run ALL tests; nothing broke.
4. REFACTOR: improve naming/structure/duplication while all tests stay green. Rerun after every edit; any failure -> undo the refactor immediately. Refactoring must not change behavior — new behavior goes back to RED.
5. TEST PYRAMID: ~80% small/fast unit tests (pure logic, milliseconds), ~15% integration (boundaries: API, DB, filesystem), ~5% end-to-end (critical user flows only). Classify by resources: small = single process, no I/O; medium = localhost only; large = external services allowed. Small tests are the vast majority.
6. WRITING GOOD TESTS: test state, not interactions (assert outcomes, not internal call sequences — interaction tests break on every refactor); DAMP over DRY in tests (each test reads as a complete specification); prefer real implementations over mocks (real > fake > stub > mock; mock only where the real thing is slow, non-deterministic, or has uncontrollable side effects); one assertion per concept; descriptive names that read like a specification (test_<unit>_<scenario>_<expected>).
7. VERIFY IN THE REAL RUNTIME: unit tests are necessary but not sufficient. For anything with a runtime surface, verify there too — a real VS Code install for the extension, a real CLI invocation, a real browser for UI. "All tests pass" with no tests actually run is a red flag; so is re-running the same green command twice with no code change in between.
8. ANTI-PATTERNS: testing implementation details; flaky/order-dependent tests; testing framework behavior instead of your code; snapshot abuse (large unreviewed snapshots); no test isolation; mocking everything; skipping tests to make the suite pass; bug fixes without reproduction tests.
