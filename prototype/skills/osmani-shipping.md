PROCEDURE osmani-shipping (production-readiness gates and reversible launches; SHIP phase):
Ship with confidence: every launch reversible, observable, and incremental. This is the operational form of "only done when production ready" — SHIP's exit gate is evidence, not optimism.
1. PRE-LAUNCH CHECKLIST — all green before deploy: all tests pass (unit, integration, e2e); build clean with no warnings; lint and type checks pass; code reviewed and approved; no TODOs or debug statements left in production paths; error handling covers expected failure modes; no secrets in code or history; native dependency audit shows no critical/high reachable findings; input validated at boundaries; auth checks in place; destructive operations gated (see osmani-security); environment/migrations/DNS/SSL configured; logging and error reporting wired; health check exists and responds; README/changelog/docs updated for user-visible changes.
2. FEATURE FLAGS: decouple deployment from release. Deploy with the flag OFF, enable for team/beta, roll out gradually (5% -> 25% -> 50% -> 100%), monitor at each stage, then remove the flag and dead path. Every flag has an owner and an expiry; clean up within two weeks of full rollout; never nest flags; test both states in CI.
3. ROLLBACK PLAN — written BEFORE the deploy, not during the incident: trigger conditions (error rate > 2x baseline, p95 latency > 50% over baseline, user reports spike, data integrity issues, security finding); rollback steps (disable flag, or revert + redeploy previous version); database considerations (migration rollback, data written by the new feature); expected time to rollback (flag: < 1 min; redeploy: < 5 min). A deploy without a rollback plan is not ready.
4. MONITORING: error rate (total and by endpoint), latency (p50/p95/p99), request volume, resource utilization, and the key business metrics; client-side error reporting that never exposes internals to users (generic error bodies, details in server logs only). Post-deploy first hour: health check 200, no new error types, no latency regression, critical user flow tested manually, logs flowing, rollback verified ready (dry run if possible).
5. ERROR-BUDGET GATE: budget remaining > 20% -> ship normally; 0-20% -> slow rollouts only, no high-risk changes; exhausted -> freeze feature work, reliability only. A high burn rate during canary is a HOLD signal even when individual thresholds are green.
6. ROLLOUT DISCIPLINE: staging first (full suite + smoke test), then production with flag off (verify health, watch errors), then team, then canary with a 24-48h window. Advance on green (error rate within 10% of baseline, p95 within 20%), hold on yellow, roll back on red. "It works in staging" is not evidence it works in production.
7. FINAL SHIP GATE — THE DEFINITION OF DONE (definition-of-done): a release ships only when BOTH hold: the release's acceptance criteria ("did we build this thing?") AND the standing Definition of Done ("is it ready?" — correctness, quality, integration, documentation, ship-readiness). The checklist above is the deploy-specific layer; the DoD is the floor beneath it. A green checklist with a failing DoD is not shippable.
