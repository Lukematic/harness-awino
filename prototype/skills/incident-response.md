PROCEDURE incident-response (production incident discipline: correlate, contain, postmortem; NO phase floor — incidents preempt the mission):
When production is broken, the mission IS the incident. Normal phase order is suspended: the incident owns the loop until service is restored, then the postmortem closes it. Mitigate first, understand second.
1. CORRELATE WITH THE MOST RECENT CHANGE — the likeliest cause of a new incident is the newest change: list deploys, config changes, flag toggles, migrations, and dependency updates in the window before onset (start with 2 hours, widen to 6 if nothing correlates); match timing AND affected surface; state a confidence level — HIGH (change matches timing and surface), MEDIUM (timing matches, surface adjacent), LOW (no correlated change). If correlated, the rollback plan written before the deploy (osmani-shipping) is the first mitigation candidate. Expand the search when nothing correlates: infrastructure changes, certificate expirations, and third-party dependency outages are not "deploys" but they break production the same way.
2. ASSESS BLAST RADIUS BEFORE ACTING — direct impact (error rate, latency, availability of the failing surface); upstream callers (who calls it — are they degrading?); downstream dependencies (what it depends on — are they healthy?); user impact (estimate from traffic volume); data integrity (any corruption or inconsistency risk?). Classify: Critical (user-facing outage, data-loss risk, multiple surfaces), Major (degraded performance affecting users, single surface), Minor (internal only, no user impact). Blast radius determines the response: rollback for change-correlated, failover or scaling for infrastructure, circuit-breaker or graceful degradation for dependency failure. A stale dependency map misses connections — check shared infrastructure (databases, queues) and external dependencies (DNS, CDN, third-party APIs).
3. MITIGATE, DON'T EXPERIMENT — restore service first, root-cause second. Every action is journaled with a timestamp. Do not refactor during the incident. Do not "fix forward" an unclear cause. Do not run experiments on production while it is broken. The mitigation is declared explicitly (who decided, what was done, what the expected effect is); the loop verifies the effect before declaring restoration.
4. BLAMELESS POSTMORTEM — within 48 hours, while memory is fresh: executive summary (what happened, impact, duration — 2-3 sentences); timeline (detection, engagement, mitigation, restoration — built from the journal, not from memory); root cause (the change or condition that triggered it, AND why it was not caught); impact assessment; action items (immediate fixes, process improvements, detection improvements — each with an owner); lessons learned (what went well, what didn't, what was lucky). Blameless means the postmortem names system gaps, not people. A postmortem that changes how the system is built or operated is filed as an ADR (osmani-adrs).
5. FEED THE LOOP — every action item becomes a tracked item or a mission with an owner; monitoring gaps feed osmani-observability; deploy-process gaps feed osmani-shipping and osmani-cicd; the incident's MTTR and its classification feed the DORA reference (dora-metrics). An incident whose action items are not tracked is an incident that will repeat.

Adapted for Awino: all Harness-MCP calls (harness_list / harness_get / harness_status / harness_diagnose) stripped — the portable asset is the workflow (correlate -> blast radius -> mitigate -> postmortem), the confidence levels, and the severity classes. "Deployment correlation" generalized to "most recent change" (config, flags, migrations, certs, third parties). Awino bindings added: rollback plan from osmani-shipping, journal as the timeline source (never memory), postmortem-as-ADR via osmani-adrs, action items as tracked items, MTTR feeding dora-metrics. Discipline only: there is no live paging integration here — this skill does not page anyone, it structures the response once the incident is declared.

Routing: NO phase floor. Incidents PREEMPT the mission — the harness injects this skill explicitly (skill_add) when an incident is declared, regardless of the current phase, and it owns the loop until restoration. It is never bulk-loaded into a turn's context. A standing floor binding would be wrong: the incident does not ride inside a phase, it suspends the phases.
