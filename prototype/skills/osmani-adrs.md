PROCEDURE osmani-adrs (record the architectural why; REVIEW phase — written when the decision is made, reviewed before ship):
Document decisions, not just code. Code shows WHAT was built; the ADR shows WHY it was built this way, what alternatives were considered, and what constraints applied. That context is what future humans — and future agents — need to avoid re-deciding the same thing six months later. One ADR per significant decision: choosing a framework or major dependency; designing a data model; selecting an auth strategy; choosing an API architecture; any decision expensive to reverse. NOT for obvious code, restating what the code says, or throwaway prototypes.

1. WHEN TO WRITE: at the moment the decision is made (PLAN for architecture, BUILD for seam changes — never deferred to the end). REVIEW checks that every significant decision in the diff has its ADR; a decision with no ADR does not ship.
2. THE RECORD: Context (the requirements and constraints that mattered) / Decision (what was chosen, stated plainly) / Alternatives Considered (each with pros, cons, and WHY REJECTED — rejected alternatives are the highest-value lines; they are what stops the re-debate) / Consequences (what this commits us to: operational load, knowledge the team must hold, doors closed). Status lifecycle: PROPOSED -> ACCEPTED -> (SUPERSEDED | DEPRECATED). Never delete old ADRs — they are historical context; when a decision changes, write a new ADR that references and supersedes the old one.
3. MATCH THE EXISTING CONVENTION FIRST: before creating one, look for the project's established pattern (docs/adr/, Documentation/Decisions/, an .adr-dir file, numbering scheme, heading set). An established convention overrides the default template — continue its sequence and format, never start a second scheme. Only when no convention exists: docs/decisions/ with sequential numbering (ADR-001-...).
4. TIMELESS LANGUAGE: write for the reader six months from now. State the decision and its rationale without anchoring to the present ("we chose X because..." — not "this week we..."). An ADR that reads as a diary entry ages into noise.
5. INLINE, COMMENT THE WHY: code comments explain non-obvious intent, never restate the code. Document gotchas inline where they matter ("this MUST be called before the first render because..." with a pointer to the ADR). Public APIs get parameter/return/throws documentation with an example; REST surfaces get OpenAPI/Swagger entries. No commented-out code (version control has history), no stale TODOs (do it now or record it properly).
