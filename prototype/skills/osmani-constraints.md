PROCEDURE osmani-constraints (decide the quality bar once, enforce it everywhere; PLAN phase):
Spec-driven development says what to build. Test-driven development proves it works. This skill defines what "good enough to ship" means — in writing, with numbers — before anyone argues about it in review. An agent writes more in an afternoon than anyone will read that week; judgment moves out of heads and into checks that run around the loop.
1. DETECT BEFORE ASKING: read the repo (manifests, test runner, linters, coverage output, CI, AGENTS.md) and report what exists in two lines. Never ask what you can read.
2. ASK FOUR QUESTIONS, each with a sane default so "I don't know" still produces a working config: (a) which dimensions beyond the floor — coverage on new code, security scanning, performance budgets, accessibility, architecture boundaries (default: coverage + security); (b) block or warn when a check fails mid-task (default: block on the floor, warn on the rest for two weeks); (c) target numbers or measure-today-and-hold (default: measure and hold — ratchets); (d) slowest check tolerated before work is handed back (default: ~90 seconds at task end, unlimited in CI). Stop at four.
3. WRITE IT DOWN: one constraints record at the repo root, committed to version control. Three sections:
   - FLOOR (always enforced, no setup): no new suppression comments (@ts-ignore, eslint-disable, # noqa, type: ignore); no unimplemented stubs or empty catch blocks; no skipped/deleted tests without a reason in the commit message; no secrets in source; the record itself never gets weakened to make a change pass.
   - ENFORCED WITH NUMBERS: each dimension names the exact command that produces the verdict — a number with no command is an aspiration, not a constraint (e.g. types: zero errors via tsc --noEmit; lint: zero errors via the project's config; coverage: changed lines >= 80% via the project's runner; security: no high findings via the native audit).
   - MEASURED, NOT YET ENFORCED: today's value + direction (must not fall / must not grow). Setting 80% on a codebase at 62% produces a red build forever, then a team that ignores red builds — ratchet from today instead.
4. PLACE CHECKS BY COST: fast checks (types, lint, secrets, floor) run after edits; task-level checks (related tests, changed-line coverage) run at task end; slow checks (full suite, audits) run in CI. A check that stalls the agent gets switched off, and a gate people switched off is worse than no gate. Scope expensive checks to the diff.
5. GUARD THE BAR ITSELF: tightening is silent, loosening is loud. At review, watch the diff for the five cheap roads to green: the threshold moved; a test got easier (skip added, test deleted, assertions pulled); a checker got silenced (new ignore/disable comments); work left unfinished (stubs, TODOs standing where implementation should be); an unexplained exception row. Compare the constraints record against its state at the branch point — `CONSTRAINTS.md` changed in the same commit as the failing feature is a red flag.
6. ESCALATION: written-only first (agents read it), then scripted (a `check` command wired into hooks/CI), then tool-backed only when the config outgrows a script. Most projects stop at scripted.
